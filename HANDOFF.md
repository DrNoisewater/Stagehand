## 4.4.1: stems split again (4.4.0 regression)

**What the user said:** after 4.4.0, "the stems dont ever seem to split", and "a forty second countdown before it even starts". A couple of weeks earlier a split took about ten seconds and the song started.

**Why:** 4.4.0 kept one stem engine open for all songs (`--serve`, jobs sent on its stdin, a thread reading stdin for cancels) and showed a guessed "time left" from past speed before the split showed any progress. On Windows the open engine never got going (most likely the stdin reader or the venv launcher in between; can't be tested on Linux), so the guess counted down from ~40 s and nothing happened.

**What changed:**
- `src/main/services/stems.js`: back to one engine process per song, as before 4.4.0 (stdin ignored, no `--serve`). Stop/cancel/jump ahead kill that process tree (`taskkill /T`, kept from 4.4.0). Removed the open-engine code (`_engine`, `_send`, `_closeWorker`, `stopGraceMs`, the speed guess).
- Time left only comes from real progress (after 3%); nothing is shown before that.
- Splits run at normal priority again (4.4.0 ran background splits below normal; with one process per song a split ahead would then stay slow after you open that song).
- `engine/stagehand_stems.py` takes `--priority` in one-shot mode. Its `--serve` mode is still there (tested by `engine_check_test.py`) but the app no longer uses it.
- `test/stems-queue.test.js` rewritten for one engine per song.
- Kept from 4.4.0: split ahead on selection, readable folders, the index (no checks that grow with the library), Smaller (Opus), parallel stem loading, live time on the menu.

**Ask the user:** does a split start right away and finish in about the old time? If not, Settings › About › the log, and the GPU/CPU it says it used.

## 4.4.0: stems: fast again, ready before you play, readable folders, smaller option

User: "Stem separation times do not update live on the menu … stem separation is taking longer the more songs I [have split] … They used to separate before the beginning of the song would play … I really want the stems to be separated before you start playing the song." Then: stem folders have "crazy" random names; could stems be zipped to save space and still load fast; does it use all CPU cores.

- **Likely cause of "slower over time":** on Windows the venv `python.exe` is a launcher; `child.kill()` only killed the launcher, so a stopped split (switching songs mid-split) kept running hidden, and they piled up. Now `taskkill /T /F` on Windows, and the engine quits by itself when its stdin closes.
- **Things that scaled with your library / stems:** `stems.ready()` hit the disk for every song on each library refresh (now an in-memory index: 3,000 songs/500 split 25 ms → 1.5 ms here; Windows disks slower); startup tidy of every stem folder ran before the window (677 ms → 2 ms; now in the background 4 s after start).
- **Warm engine:** `engine/stagehand_stems.py --serve` keeps torch and the model loaded between songs (jobs as JSON lines on stdin, cancel between chunks, frees GPU memory after each job, quits on stdin EOF or 10 idle min). One-shot mode, `--check`, `--prefetch` unchanged. StemService uses one worker; a job that doesn't stop in 4 s gets the worker closed.
- **Wait for stems:** the 15 s full-mix fallback (`WAIT_MAX_MS`) is gone: with "Wait for the stems" on, the song starts when its stems are in (Play now still works; failure/cancel plays the full mix).
- **Time left, live:** `eta`/`etaAt` from progress speed (or past splits before progress), `ui.js stemsLeft()`, a 1 s ticker; on the top pill, its menu (rows now update in place; rebuilding them lost Cancel clicks), the highway panel and the wait card.
- **Split ahead:** selecting a song (600 ms debounce) queues its split (`stems:ahead`, last 3 picks only, never stops a running split).
- **Readable folders:** `Stems/Artist - Title [1a2b3c4d]/<model>/`; the full key is in meta.json; old hash folders are renamed in the background (in-use ones next start). `stagehand://stems/<key>/…` resolves through the index.
- **Loading:** stems load in parallel (6×3 min FLAC: 1.87 s → 1.0 s in Chromium).
- **Storage choice** (Settings › Stems): Lossless (FLAC, default) or Smaller (Opus 192, ~1/6 the size; loads a bit slower: 1.6 s vs 1.0 s), convert-existing button with space saved, total size. Zip wouldn't help (FLAC is already compressed).
- **CPU:** "full" = all physical cores; the split you're waiting for runs at normal priority, background splits lower and on CPU at half the cores while a song plays (set from inside Python). Each split logs device, cores, threads and the time of each step (decode, engine start, model, separate, write, save).
- Tests: stems-queue.test.js rewritten (serve protocol, stop, eta, split ahead, folder rename/lookup), engine_check_test.py (serve without torch), codec-chromium ok, ui3: all stem checks passed incl. "keeps waiting for slow stems"; the "FLAC only" check was updated for the new choice (not re-run); "Jam … Fluid picture" failed on a Fluid `splats` error unrelated to this change.
- Not verifiable here (Windows only): taskkill of the tree, SetPriorityClass, renaming a folder with a file open.

**Ask the user:** is splitting quick again, and does the song now start with its stems? Does the time left look right? Can they find songs in the Stems folder? Smaller as the default for new splits? Is keeping the model in GPU memory for 10 idle minutes OK alongside games?

## 4.2.1: the neck lights up as notes arrive

User sent three Rocksmith clips (Bleed It Out, a bass solo at frets 12–15): "focus on how the notes light up once they reach the playing area … the square lights up and the notes show and light up as they're getting closer/getting hit. See if we can mimic that behavior more."

Measured frame by frame (60 fps) in the clips. Before this, Stagehand only lit things after a note landed (hit posts and flares when scoring; a soft flash without). Rocksmith lights them **before**, whether or not you play:
- **Note spots on the neck**: each coming note's place (its string, its fret) shows as an outline in the string's colour about 1 s early, brighter as it closes in, white-hot rim and a halo in the last moments and while it rings, then fades. One per string+fret (the soonest note).
- **Fret wires light up** as white posts with a warm pink glow ~0.16 s before the note lands, brightest as it lands, dimmer through its sustain, fading 0.22 s after. Chords: at the frame's edges; open strings: at the hand position's edges. A missed note's posts go dark when it's judged. The pink hit posts and flares are unchanged on top.
- **The chord's box at the neck** (the "square"). First try was thin lines up to the chord's top string; user: "the single notes look much better, but the chords do not have the same highlighted box that Rocksmith has". Now, measured again: a rectangle as wide as the chord's frame and as tall as the neck (under the bottom string to above the top one), thick solid cyan edges, a soft halo fading outward, brighter top corners, faintly lit inside. It starts lighting 0.5 s before the chord (`BOX_LEAD`), flashes as it lands and stays faintly lit 0.6 s after (`BOX_HOLD`), so a strummed passage keeps its box. Then (user: "we can get a little closer and still soften it a bit"), next to the clip at the same moment: thin cyan neon lines with a soft glow along the top and bottom instead of thick bars, pink-white posts for the sides (as in the game), the top just above the top string (it was well above), small corners, barely lit inside, and the flying chord frame no longer draws once it reaches the neck (it showed as a second, smaller box inside; its notes still land).
- The flying gem's rim turns white in its last 0.1 s.

All in `buildApproach` (highway.js, "approach" section; `TARGET_LEAD`, `POST_LEAD`, `POST_FADE`, `postLight`), drawn after the neck, before the notes; depends only on the song clock, so it also shows when paused or scrolling. Not done for the 2D fallback highway (highway-classic.js).

Look tool repairs (test/hwlook had drifted from 4.2): stubs for the names the app now imports (rig `P`/`openStrings`, tab `createTabView`, tonelib/captures/realamps), a quiet `api` stub, a `drums.js` stub (the real one starts before the song player in the harness's load order), the page's other elements in index.html, and the first-time timing check offer turned off so it doesn't cover shots. `seq.js` now takes a made-up scene (A/B/C/T) instead of a chart file and finds its own folder. `VERIFY=1` still looks for the old "Highway options" button (stale since 4.2.0).

## 4.1.2: recorded videos' sound, fixed for good (the seventh report)

- **Cause found:** nothing in the recording path changed since 4.0.7 (checked: the committed `stagehand-audio.exe` does send the full mix, frame type 5, disassembled). But the **Recordings window played videos with a plain `<video>` element**, i.e. to Windows' default speakers, the only player in the app not going through `engine.extraOut()`. With the sound engine holding the output exclusively (fastest mode, the user's choice), that sound is shut out, so the videos *seemed* silent. - **Fix:** `recordings.js show()` sends the player's sound through `createMediaElementSource` → `engine.extraOut()` (with `crossOrigin`), and `main.js serve()` adds `Access-Control-Allow-Origin: stagehand://app` to `stagehand://take/…` (without it the browser passes silence: cross-origin).
- **Rock solid, not reported afterwards** (user: "the saved but no sound can not happen … recording 4 minutes to be told sounds weren't included … it has to be rock solid"). The after-the-fact "has no sound" message is gone; instead:
  - **Sound check before recording** (`take-video.js soundCheck`): the recording only starts once the engine's sound reaches the recorder; if not, it asks the engine again, then restarts it once; if still nothing, it doesn't start and says why within ~5 s.
  - **Found a real hole:** when the sound engine restarted mid-recording (crash, cable bumped, sleep, device change; `autoStart` brings it back), the new engine never sent sound to the recorder or looper again: the rest of the recording was silent (clip-chromium shows 0 after the crash on the old code). Now `rig.monitorOn()` runs in every `rig.start()`, and the recorder's watchdog asks again every 0.4 s while sound is missing and says "Sound dropped out" on screen after 1.5 s (and "Sound is back").

### How it works

**Engine (native/dsp/sh_nam.c, plain C, no libc; native + WebAssembly):** a port of NeuralAmpModelerCore (MIT). Loads `.nam` JSON (own JSON parser, weights straight into floats), runs LSTM, WaveNet A1 (nano…standard, custom) and A2 (bottleneck, grouped convs, gated/blended, all 8 FiLM points, head1x1, post-stack head with kernel > 1, condition DSP), slimmable WaveNets at full size, SlimmableContainer (largest submodel; `size_pref` 1 = smallest). Block processing over time (NB = 256) so the inner loops vectorise. Prewarm = same sample counts as NAM. Fast float-accurate tanh (rational, < 4e-7). **Matches the reference to ~1e-6 relative on every example model** (`test/fixtures/nam`; recipe to rebuild the reference below).
- `namamp_build` (sh_nam.c): the amp block. Input trim = `(tone gain − gainRef) × 12 dB` (gainRef = the gain position the chosen model was captured at), then the tone's Bass/Mid/Treble/Presence as post-EQ around noon (±7/6/7/4 dB), DC blocker, user knobs via `sh_block.user` (amp_user dispatches). Resampler (16-tap windowed sinc, 512 phases) when the capture's rate ≠ device rate: ~79 dB clean, 0.3–0.5 ms extra (`native/test/rs_test.c`). Gate threshold from a measured "squash" (quiet vs loud gain), cached per capture.
- `sh_engine_set_nam(e, slot, json, len, full_rig, gain_ref, trim_db)` + `sh_engine_nam_error()`. Parsed model per slot in a 2 MB region after the slot arenas (`NAM_BYTES`); refuses the playing slot. `full_rig` skips cab blocks and the default cab. Build with a standard A1 capture ≈ 250 ms (was ≤ 81 ms modelled).
- CPU here (Xeon 2.8 GHz, SSE build): A1 standard ≈ 15% of a core at 48 kHz/128, A2 full ≈ 9%, whole tone with A1 standard ≈ 17% (24% at 44.1 kHz with resampling). `-march=x86-64-v3` would give ~10%.
- Helper: `{"cmd":"nam","slot","path","fullRig":0|1,"gainRef","trim"}` reads the file, answers `{"ev":"nam","slot","ok","error"}`; does **not** rebuild (the page builds next). Re-applied on engine re-init. wasm: `buf_nam()`, `buf_nam_size()` (4 MB), `set_nam(slot, len, full, ref, trim)`, `nam_error()`.

## Guitar engine (v2.0.0)

The user asked for the engine redesign and better tones in one update. Answers they gave: they listen mostly through **speakers** (sometimes headphones) on the PC, use **ASIO4ALL** with Rocksmith, **Rocksmith feels good to play** (that's the latency target), and **taking over the output is fine**.

- **Native path:** rig.start() first moves the player onto the native route (AudioContext sink `{type:'none'}` + song-tap worklet → MessagePort → main → helper stdin), because Windows refuses exclusive access while any shared stream is open on the device. Then `start` (exclusive, falling back to shared with a notice). The helper mixes the song with the amp. `engine.extraLatency` = helper's songLatencyMs so `engine.position` stays in sync.
- **Song clock drift:** Chromium's `none` sink clock runs about 0.27% slow (measured). Resampling to follow it would bend pitch, so the song goes through a splicer (WSOLA-style skip/repeat of 4–30 ms at the best-matching point, 6 ms crossfade) and only a fixed-ratio resample. `native/test/slip_test.c` checks ±2% drift keeps 440.00 Hz.
- **Guitar path:** capture ring → small drift resampler (max ±0.1%) → engine → output. Target fill = in period + part of the out period + 24 frames.
- **Song route (2.0.1):** the user reported the song didn't play with the guitar on (2.0.0). Likely cause: the tap worklet *transferred* its ArrayBuffers to a port entangled with Electron's main process, which drops them. Now audio is copied, and if the helper's meters show no song for 1.5 s while playing, `engine.useSongRelay()` sends it through the page instead (remembered in localStorage `stagehand.songRelay`). `SH_DROP_DIRECT=1` / `SH_RELAY=1` exercise these in rig-chromium.js. Ask whether the song plays now and whether there was a ~1.5 s silent start the first time (= relay kicked in).
- **Fallbacks:** engine choice in the rig panel: Fastest (exclusive) / Shared / In-app (WebAssembly). Auto falls back native-shared → in-app with `rig.notice`.
- **Tones:** song tones carry their full GearList (`tones.js` mapTone → `gear`), built per song into engine slots ahead of time (`rig.prepareTones`). Presets are gear chains too (rig.js TONES). User knobs: gain absolute (−1 = tone's own), bass/mid/treble/fx offsets around 0.5.
- **Calibration:** "Set level" in the rig panel (4 s strum → input knob so peaks hit −6 dBFS).

## Conventions

- **Visual first (the user's standing rule for everything we make):** "why read when you can see immediately?" Convey state with colour, icons, glow, motion and position before words; keep text short and secondary. Example: a volume at 0 shows as a red, pulsing, crossed-out speaker, not a paragraph.
- **Key controls always in reach:** song volume is in the bottom bar, your guitar's volume on the guitar card (bottom left); a short toast with "Turn it up" appears if you press play with either at 0 (the user lost time hunting for a 0 volume).

- **UI copy:** plain and friendly, typographic apostrophes (’), no jargon.
- **CSS class names:** check for collisions before adding.
- **Menus and toasts:** z-index 300 so they show above the highway (z 200).
- **Renderer:** no frameworks, `h()` / `icon()` / `showMenu()` / `toast()` from `ui.js`.
- **Before shipping:** verify UI changes with an e2e run and screenshots.
