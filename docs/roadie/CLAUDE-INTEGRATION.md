# Implement The Roadie in Stagehand Song Finder

Use the supplied Stagehand-SongFinder-Roadie assets as the approved visual direction. This update is scoped to Song Finder only. Work directly in the current Stagehand source, inspect the actual toolbar, layout system, media renderer and existing search/download/import callbacks before editing. Preserve unrelated features and current song-acquisition behavior.

## 1. Toolbar layout
- Replace the three circled status *indicators* with the illustrated Roadie component. The red circle was an annotation only; never put a screenshot or red circle into the application.
- Slightly increase the Song Finder top toolbar height. Start at 66–70 DIPs total, with a 240 × 57 DIP art slot (approximately 4.2:1), centered vertically, aligned after Next song, before existing explanatory text. Adjust to actual existing toolbar and available width; 210 × 50 DIP fallback on narrower windows. Preserve aspect ratio and all artwork; do not stretch or crop the character.
- Existing back/forward/reload, search query, FIND, Next song and status copy must remain accessible. Do not replace functional buttons with the illustration: if any existing status button is interactive, retain its action and focus/accessibility through a labeled adjacent control or suitable equivalent. Let explanatory text truncate with tooltip if necessary, not navigation. Keep one horizontal row where feasible and preserve space for search results. DPI-aware layout, no fixed physical pixels.
- Preserve the approved worn comic artwork, dark backstage palette, amber searching/downloading and lime green success. No new generic icons, AI dashboard styling, stickers, random extra controls or substitute character. Existing text outside the badge gives exact status (including Importing and errors), even in frames where the illustration does not contain a word.

## 2. Bind real state, not a timer
Locate existing job events; use their real identifiers and marshal onto the UI thread. Map actual searching, confirmed result (optional), download start/progress, import start, and committed library success to the clip mapping in README and manifest. Await actual durable library/index completion before allowing success. Preserve existing progress/error/retry/cancel behavior. For actual byte progress display a discreet percentage in existing status text when total is known; no invented progress. Never play 'In Songs' before the import succeeds. A search-result page may remain open indefinitely: keep search/ready state as appropriate; do not imply a download has started. Do not automatically start a download because of an animation.

Implement a view-only state machine with a current job token, actual state, visual state, and a pending next search. Ignore duplicate/stale progress and callbacks, cancel/dispose previous playback when appropriate. Download/import/failed events for newer jobs interrupt an old celebration; if next search starts immediately, allow the success animation to finish visually (~3 seconds) while the actual next search proceeds, unless more urgent work starts. Then play reset and enter search. Do not cycle automatically when idle. For concurrent jobs follow the currently displayed/selected Song Finder job; don't mix events across jobs. Import failure must never look successful. Closing the window cancels only visualization resources, not backend work.

## 3. Playback / performance
Prefer the current native accelerated media/render path. Use individual silent 60fps H.264 clips. Preload likely next clips using supported player APIs, keep last poster visible during swaps, loop holds seamlessly and avoid decoding multiple clips continuously. Do not introduce a heavyweight WebView just for an animation. If Stagehand is already web-based, `roadie-player.js` demonstrates the contract; production code needs app-specific event wiring and local asset paths. If the platform cannot play H.264 reliably, choose an existing accelerated renderer or approved transcode; don't silently use the original rapid GIF. Respect reduced motion (static poster for real state), hidden/minimized windows, playback failures and UI disposal. No external services, no audio output, no network fetches, no mandatory dependencies for this purely visual feature. Target native 60fps (16.67ms frame budget); measure actual playback and UI responsiveness under load. Source clips are 60fps interpolated, not fully hand-animated; preserve the character design if adjusting interpolation artifacts.

## 4. Acceptance checklist
- Toolbar slightly taller; roadie artwork clearly legible at 100%, 125%, 150%, 200% display scale. Window resize cannot hide key controls.
- Slow searching, eye sockets aligned with binoculars, bulging-eye gag; real found result shows triumphant record; download places record on the computer deck; import produces composition; success shows paper tossed into overflowing music pile, roadie relaxed in swivel chair.
- All art matches approved supplied frame set. The real UI state, actual progress and backend error messages remain correct.
- Test prolonged lookup, cancelled lookup, manual song selection, failed download, retry, slow download, unknown content length, fast download/import, duplicate callbacks, failed import, new job during celebration, minimized/closed window and reduced motion.
- Test native playback on the target Windows configuration; no excessive CPU/GPU, audio, memory leakage, flicker, whole-window invalidation or input latency. Verify existing Song Finder functions still work.
- Build/test and report changed files and how real events map to the visual state. Do not claim native 60fps without measurement, or unrelated changes without approval.
